MDI ships as a library kit — not a monolithic platform.

Multiple project teams across the org do document extraction independently — each reinventing the pipeline. Part A — For Business Stakeholdersnon-technical

The problem we solve

Every business receives documents from many vendors in many formats. Each one needs structured data extracted — vendor, account, dates, totals, line items, terms. Today this happens via manual data entry, per-vendor templates that break the moment a layout changes, or rigid OCR rules that don't generalise. MDI replaces all of that with a learning document brain.

How it works (the simple version)

When you upload a document, six "organs" of the brain work together — and remember what they learned for next time.

👁
Eyes
Looks at the document and identifies what it is — telecom invoice? insurance policy? purchase order?
🧠
Memory (Hippocampus)
Asks "have we seen this before?" — reuses what it learned, or discovers a new pattern.
✋
Hands
Reads out every field — vendor, account, dates, amounts, line items, addresses, terms.
⚖️
Conscience
Cross-checks the maths and flags anything suspicious (totals that don't add up, expired terms).
💡
Insight Cortex
Surfaces what's interesting: recurring vendors, pricing outliers, contracts about to expire.
📝
Brain memory
Stores the pattern + every correction, so the next similar document is faster and more accurate.

Key design decisions + reasoning

DecisionReason
Open-vocabulary schema (not fixed templates) Vendor layouts change constantly; templates need maintenance. Pattern Cortex discovers fields per-document; the canonical-alias layer keeps names stable downstream.
RLS + non-superuser app role Tenant isolation enforced at the DB. App bugs cannot leak cross-tenant data. FORCE ROW LEVEL SECURITY at every migration.
Two-engine DB pool App routes use mdi_app (NOBYPASSRLS). Admin cross-tenant routes use mdi (superuser). Separate pools prevent accidental scope creep.
Provider fallback chain Gemini is cheap but rate-limits. Claude is the resilience layer. Same prompt contract; router walks the chain on retryable errors.
Heuristic extractor as Quick mode LLM availability is never 100%. Regex floor gives an always-on path. Production-grade docs extract 6 fields in 150 ms with provenance.
pgvector instead of a separate vector DB One DB to operate + back up + secure. HNSW scales to millions of vectors. Cross-table joins (extractions ↔ patterns) stay relational.
Pack abstraction (YAML, no Python) Adding a vertical is a config commit, not a code release. Pack augmentation unifies LLM discovery + pack-declared fields.
Per-value provenance (source_text) Every extracted field carries the substring that drove it. Audit + compliance + analyst trust.
Self-hosted Langfuse Trace every LLM call without sending prompts / customer data to a 3rd-party cloud.
8px grid + WCAG AA Accessibility by design. MUI Material 3 tokens default-compliant.

1. Self-training & continuous learning

The brain already memorises patterns and embeds analyst corrections, but the feedback loop only closes when someone opens a document. The capabilities below let the loop close on its own — the platform improves measurably each week without manual intervention.

Capability Priority What it does
Active learning queue P0 Any extraction with confidence < 0.7 — or where two providers disagreed — drops into a review queue with the source text already highlighted. One analyst click ⇒ embedding written ⇒ all similar future docs benefit. Today this exists implicitly; surface it as a first-class queue with a weekly KPI ("docs improved this week").
Correction propagation P0 When an analyst corrects a value, run an ANN search over the existing corpus and silently re-extract the top-K most-similar documents. Today we only bias future extractions — this also fixes past ones retroactively.
Pattern confidence decay P1 Patterns not re-seen in 90 days lose weight in the matching score. Prevents stale layouts from dominating when a vendor changes their template.
Auto-pack auto-promotion P1 After an auto-pack proposal scores ≥ 0.85 confidence across N consecutive successful matches, promote it to a first-class pack automatically. Today promotion is manual.
Few-shot from corrections P1 At extraction time, pull the 3 most-similar prior corrections via pgvector ANN and inject them as ad-hoc few-shot examples in the Hands prompt. Today corrections only bias post-hoc — this fronts them straight into the model's context.
Synthetic doc augmentation P2 Once a pattern has 5+ corrections, ask Gemini Pro to generate 20 synthetic layout variations + value pairs. Feeds the regex catalogue and the evaluation harness without waiting for real-world drift.
Per-tenant prompt overrides P2 Each tenant supplies a 200-word "house style" preamble prepended to the Hands prompt. Encodes things like "we always treat 'Net 30' as Net-30 from invoice date, never receipt date."
Tenant-scoped fine-tuning P3 Once a tenant has 10k+ corrections, fine-tune a small open-weight model (Llama 3 8B) per-tenant. Their docs route through the fine-tune first, fall back to Gemini on low confidence.

2. Domain- & dataset-specific extensibility

Some verticals carry rules that can't be discovered from documents alone — they live in a domain expert's head or in a customer's ERP. We need clean lanes to inject that knowledge without writing Python every time.

Three lanes for adding domain knowledge

Lane For whom Mechanism
YAML pack Domain expert
(no Python)		 Drop a YAML file into packs/<industry>/: schema, rules, validators, enrichment tables. Hot-reloaded by the orchestrator. Already works for insurance + telecom — primary lane going forward.
Code-bridge handler Engineer
(vetted Python)		 Register a Python callable in brain/handlers/. The LLM dispatches by name but never executes — the bridge keeps the model out of the call stack. Use for: tax-rate lookups, live FX conversion, ERP API calls, business-logic validators.
Dataset bootstrap Customer
(zero-code)		 Upload 5–10 labelled examples through the UI → an LLM-as-judge generates a draft pack YAML + regex catalogue → customer reviews and commits. Best for niche customers ("we want to extract X from our supplier's PO format").

Example — what a customer-uploaded bootstrap sample looks like

# POST /admin/bootstrap-pack — 6 labelled samples is usually enough { "vertical": "logistics", "vendor_hint": "DHL", "samples": [ { "file": "sample-1.pdf", "labels": { "awb_number": "7651234890", "origin": "DEL", "destination": "FRA", "weight_kg": 12.4, "chargeable_weight_kg": 14.0, "freight_charge_usd": 187.50 } } // ... 4–9 more samples ... ] } # Brain returns a generated pack scaffold: # - schema/fields.yaml ← 6 field definitions inferred # - rules/validators.yaml ← weight ≤ chargeable_weight invariant # - prompts/awb.md ← air-waybill-specific prompt # - heuristic regex patches ← AWB number format (10-digit, optional dash)

Domain glossary vector store

For domain-specific terminology (medical codes, telecom acronyms, legal Latin), the customer uploads a glossary CSV. Each term is embedded; both the chat layer and the Hands stage ANN-lookup unknown terms to resolve them.

# telecom-glossary.csv term,definition,canonical MRC,Monthly Recurring Charge,monthly_recurring_charge NRC,Non-Recurring Charge,non_recurring_charge USF,Universal Service Fund fee,usf_surcharge CSR,Customer Service Record,customer_service_record SIP DID,Session Initiation Protocol Direct Inward Dial,sip_did_number

When to hard-code Python (and how to keep it safe)

Most domain rules belong in YAML. But some — live FX rates, tax tables, ERP joins — need real code. The code-bridge pattern is the only sanctioned way:

# brain/handlers/fx_convert.py from mdi.brain.bridge import register_handler @register_handler( name="fx.convert", description="Convert an amount between currencies using daily ECB rates.", schema={"amount": "float", "from": "str", "to": "str"}, ) def fx_convert(amount: float, from_: str, to: str) -> dict: rate = _fetch_ecb_rate(from_, to) # cached, daily refresh return {"value": amount * rate, "rate": rate, "source": "ECB"} # The LLM emits {"call": "fx.convert", "args": {...}} in its output. # The bridge validates against the schema, runs the handler, splices # the result back. The model NEVER executes Python — only describes it.

Part D — MDI Kit v1 initiativecommitted

This is the current build direction. Everything in Parts A/B/C still holds — but how we ship it changes: the extraction brain is packaged as a Python library any project team can embed, not a platform every team logs into. Studio remains for pack authoring and correction review. Full API design contract lives in MDI-KIT-DESIGN.md at the repo root.

1. Two products, cleanly separated

Product What it is Who uses it Ships as
MDI Kit
(new — the library)		 The extraction brain, packaged. Import it, pick a pack + filters, get JSON out with confidence + provenance. Engineers embedding extraction into their own apps. pip install mdi-kit · CLI · Docker image · REST client (stub)
MDI Studio
(what's built today)		 The hosted UI + shared learning + pack-authoring surface. Existing FastAPI + Next.js stack. Pack authors · analysts reviewing extractions · admins. Existing platform, imports from mdi-core.
Rule of thumb: Studio produces packs. Kit consumes them. Kit runs in each team's own environment; Studio is where the brain matures. This separation turns MDI from "another platform" into an "extraction primitive."

2. What a consumer's code looks like

from mdi_kit import Brain brain = Brain( pack="finance/invoice_v1", filters=["vendor", "amount_due", "line_items", "due_date"], ) result = brain.extract("path/to/invoice.pdf") print(result.fields) # {vendor: "GEORGETOWN PAPER STOCK", amount_due: 12450.00, ...} print(result.confidence) # {vendor: 0.94, amount_due: 0.98, ...} print(result.source_text) # {vendor: "GEORGETOWN PAPER STOCK\n1234 Mill Rd", ...} ← provenance

That's the whole embedding cost for a project team. No pipeline setup, no LLM keys in their code, no pgvector. If they want learning + corrections, they graduate to stateful mode with their own Postgres. If they want a UI on top, they wire Studio.

5. The enabling refactor — repository restructure

Today mdi/src/mdi/ is one monolith. To ship a library cleanly, split into four packages under a monorepo. Studio keeps working — it just imports from mdi-core instead of owning it.

mdi/ packages/ mdi-core/ ← pure extraction pipeline · no HTTP · no UI mdi-kit/ ← consumer-facing library · imports mdi-core mdi-studio/ ← existing FastAPI + Next.js · imports mdi-core mdi-packs/ ← YAML packs · published to git-backed registry

This is the first tangible step and unblocks everything else. It's also the highest-risk item because the current code has HTTP handlers, DB session management, and pipeline stages tangled together. Untangling them is 1–2 weeks of careful work — but everything downstream is mechanical once it's done.

7. Technology stack — what earns its keep

Layer Choice Why
LLM provider Vertex AI primary + Claude via Bedrock fallback Vertex gives enterprise auth, org-level quotas, VPC, per-project GCP billing — critical when multiple project teams consume the same kit. Existing gateway abstraction keeps the swap clean.
Observability Self-hosted Langfuse, one instance per consuming project OR shared with project-tag scoping Each project team sees only their own traces. Kit auto-tags every LLM call with project_id — no cross-project data leakage.
Parsing pdfplumber + Docling Already in the stack. Docling gives layout-aware parsing for tables.
Embeddings bge-m3 (local via sentence-transformers) No per-team API key. Ships inside the kit.
Vector store pgvector in caller's Postgres OR ephemeral in-memory Kit supports both. Teams that want learning bring a DB; teams that want extract-and-forget don't.
Pack registry Git-backed (private repo per org), OCI later Packs are YAML — versioning + PR review + rollback come free from Git. Teams mdi-kit packs pull finance/invoice_v1@2.3.
Filter primitives Declarative composition layer over packs Teams compose ["vendor", "amount_due"] from any pack that defines them. Kit resolves + runs.
